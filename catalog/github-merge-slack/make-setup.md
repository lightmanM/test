# Make Bridge setup for "GitHub merge → Slack"

One-time setup in the owner's Make account (zone `us2.make.com`). The demo then creates one
scenario per tester from the Bridge template; testers connect GitHub and Slack in Make's popup.

If the account has no **Bridge** option (Templates page has no "+ New Bridge template"), stop:
the demo shows this workflow as "Deploy unavailable".

## 1. Import the prepared blueprint

`blueprint.json` in this folder is the team's scenario with two changes (generated by
`scripts/build_catalog.py`):

- a filter **"Recently merged pull requests only"** in front of the commit lookup:
  `{{1.merged}}` = true (updated-but-unmerged PRs no longer make the scenario fail) **and**
  `{{1.mergedAt}}` later than `{{addMinutes(now; -20)}}` (the trigger watches *updated* PRs, so
  without this a comment on an old merged PR would post its diff again);
- the owner's connection IDs removed.

1. Make → Scenarios → Create a new scenario → ⋯ → **Import Blueprint** → choose `blueprint.json`.
2. When asked, create/select test connections for GitHub and Slack (only to configure the template).
3. Check the filter between module 1 and module 2: `merged` **Equal to** `true` (boolean) and
   `mergedAt` **Later than** `now − 20 min` (date). Adjust if Make named the fields differently.

## 2. Make the repo and channel per-tester inputs

The scenario still has sample values: repository `heroliy-sketch/auto-workflow` (module 1 and
the URL of module 2) and Slack channel `C0C5E88SKSP` (module 3).

1. Module 1 (Watch Pull Requests): repository owner and name → mark as **end-user inputs** in the
   Bridge template (step 3), labels "Repository owner" and "Repository name". Set "choose where
   to start" to **from now on** so old PRs don't post.
2. Module 2 (Make an API call): set the URL to use the same owner/name inputs:
   `/repos/{{owner}}/{{name}}/commits/{{1.mergeCommit.abbreviatedOid}}`.
3. Module 3 (Create a Message): channel → end-user input "Slack channel".
4. Scheduling: every **15 minutes**.

## 3. Save as a Bridge template

1. Templates → **+ New Bridge template** → based on this scenario.
2. Expose the connections (GitHub, Slack) and the inputs above to end users.
3. Publish the template; note its **template ID** → `MAKE_BRIDGE_TEMPLATE_ID`.

## 4. Bridge application key

1. Bridge settings → Applications → create an application for the demo; set the allowed
   redirect URL to `<PUBLIC_BASE_URL>/make/callback` (the demo appends `?state=<signed token>`;
   if Make requires an exact match, allow the URL with any query string).
2. Secrets → create a secret; note the **key ID** and **secret** → `MAKE_BRIDGE_KEY_ID`,
   `MAKE_BRIDGE_SECRET`. The demo signs a 2-minute HS256 JWT `{sub: "workflow-demo:<username>",
   jti, iat, exp}` with `kid` = key ID per request, so each tester gets their own Bridge sandbox.
3. Demo settings: `MAKE_BRIDGE_TEMPLATE_ID` (step 3), `MAKE_ZONE` (default `us2.make.com`) and,
   if the template lives in a specific team, `MAKE_TEAM_ID`.

## 5. Verify

- [ ] The workflow card is available (the demo calls `GET /integrations/` for a setup-check user;
      a 401/403/404 shows "Deploy unavailable: Make Bridge isn't enabled for the owner's account").
- [ ] A test user deploys: Make's popup asks for GitHub, Slack, repo and channel; the demo shows
      the deployment as active.
- [ ] Merge a PR in the test repo → Run now → diff posted in the channel; run listed in the demo.
- [ ] Delete removes the scenario from the Make team.
